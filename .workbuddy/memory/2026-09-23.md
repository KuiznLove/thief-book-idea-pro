## 图标素材可行性调研（用户提问，尚未实施）

用户问"所有按钮图标能否改用开源素材、不用手绘矢量图"。调研结论：

- **平台原生支持 SVG 图标**：`IconLoader.getIcon("/icons/x.svg", MyIcons.class)`（路径必须以 `/` 开头，**2023.3 上探针编译验证通过**）；暗色变体同目录加 `_dark`（`iconName_dark.svg`）、HiDPI 加 `@2x`，平台按环境自动挑选；SVG 需声明 `width`/`height`（缺省 16×16）。官方图标文档另有 New UI 的 `expui/` + `IconMappings.json` 机制（本项目没接 New UI 图标映射，暂不涉及）。
- **关键约束——运行时颜色**：`AssistantIcons` 的 12 个图标都接收 `Color` 参数，16 个调用点依赖它（悬停/激活/状态色，如 speaker 播放变绿、sidebar 两态）。而 **2023.3 平台没有给插件图标染任意色的公开 API**：`IconManager`、`ColorPatcherStrategy`、`SvgAttributePatcher` 这些类只出现在 2025.3 平台的 jar 里，2023.3 的 `lib/*.jar` 搜不到；官方文档也只给了 `_dark`/`@2x` 这种**静态**变体。
  → 换素材必须二选一：**a)** 加一层 tint（渲染源图标 → 按 alpha 用目标色填充 → 缓存，约 40 行纯 AWT，无版本风险）→ 保留现有 API、16 个调用点零改动、且不需要 `_dark` 文件（颜色来自 `AssistantTheme` 的 JBColor，自动跟主题）；**b)** 放弃动态色，为每种颜色存一份 SVG（文件数翻倍，不推荐）。
- **素材 license**：Lucide = ISC、Tabler = MIT、Feather = MIT、Bootstrap Icons = MIT、Material Symbols = Apache-2.0（都要在 `resources/icons/` 放许可声明并在 README 注明）。平台自带 `AllIcons`（Apache-2.0）零素材、风格最像 IDE，但**不能任意改色**（New UI 下平台会把图标内容色改成白色），满足不了状态色，不适合用在这批按钮上。
- **可换的 11 个**：copy / download / refresh / check / play / arrowUp / chevronDown / chevronLeft / chevronRight / image / sidebar(两态) / speaker(两态)；**建议保留**：`brand`（品牌图形，素材无对应物）、`fileBadge`（画的是文字角标 PY/JAVA/SH，不是图标）。
- **实施注意**：Lucide 是 24×24 viewBox + 2px 描边，画到 15~16px 会偏细，需把 `stroke-width` 提到 2.5~3；`currentColor` 要替换成具体色（或交给 tint 覆盖）。改完跑 `.workbuddy/tools/IconPreview.java` 核对形状；`UiPreview` + `PngDiff` 会出现差异（图标形状变了，属预期）。
- 现状图标预览：`.workbuddy/preview/icons-now.png`（`IconPreview` 放大 8 倍，手绘质量其实不差）。

### 真正的根因：不再用 ImageIcon + tint，改成"按绘制倍数自己光栅化"

用户第二次反馈"还是很糊"（附截图）。复盘：**上一轮改错了地方**。

- **真正的根因**：`tint()` 最后 `new ImageIcon(位图)`，位图尺寸 = **逻辑**尺寸（16px）。2x 屏上 Swing 把这张 16px 位图**插值放大**成 32 设备像素——糊的是这一步，与 tint 内部比例算得准不准无关。上一轮把分母改成 `JBUI.scale(...)` 只是让那张 16px 位图更准，它仍然是 16px。
- **平台依据（实查 2023.3 的 jar，不是猜）**：`com.intellij.util.ui.JBHiDpiScalableIcon(Image, int w, int h)` 的语义就是"持有设备分辨率位图 + 报告逻辑尺寸"，`paintIcon` 直接 `drawImage` 不缩放；`CachedImageIcon` 也按 `GraphicsConfiguration` 挑分辨率 → 正确做法是自己按目标像素光栅化后 1:1 落笔。
- **新实现（`AssistantIcons$SvgIcon`）**：读 SVG 源码 → 矢量层把 `#000000` 换成目标色 → `SVGLoader.load(is, size × t / 24)`（`t` = 绘制时 Graphics 的变换倍数）→ `g.drawImage(raster, x, y, size, size, null)`。两种 HiDPI 模式（Graphics 已缩放/未缩放）都 1:1，**不必判断当前是哪种**；位图按 `(名称, 像素, 颜色)` 缓存。顺带不再依赖 `IconLoader`（无 Application 时它 `getIconWidth()` 返回 0，根本解析不出图标）。
- **量化验证（新增 `.workbuddy/tools/IconHiDpiCheck.java`）**：与"同一渲染器渲染的参考图"逐像素比对。14 个图标 × {plain, scaled} × {1x, 2x} 全部 **0 差异**；同样的检查对旧实现是 44%~76% 差异。**参考图必须先换成和被测图标一样的颜色**，否则比出来的是颜色差（一开始忘了换色，白跑一轮）。

## 两条横栏的图标"从高度上没对齐"（已修，已打包）

用户确认"图标不糊了"，随后附两张截图反馈：顶部栏与底部输入框工具栏的**左右两组图标垂直方向没对齐**。

- **根因**：顶栏/底栏原来都是"左侧一个 `FlowLayout` + 右侧一个 `FlowLayout` + 中间留白"的两段式。`FlowLayout` 只把自己**那一行**的子组件按"行内最高元素"居中，两侧面板各算各的标高 → 只要两侧最大高度不同（字号 / DPI / 图标尺寸任一不同就会不同），两组中心线就错开。用户 HiDPI 环境实测：顶栏两侧中线差约 **6 设备像素**、底栏约 **13 设备像素**（底栏左侧的 @/#/图片按钮只有图标、右侧有更高的模型按钮与发送键，标高差更大）。
