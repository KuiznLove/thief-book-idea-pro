# v0.3.3 重构评估（2026-09-23）

评估范围：`481ca58`（first commit）→ `78b42cb`（v0.3.3：抽取 book 读取引擎 + 稳定性修复）→ `3498e14`（图标小修）。

## 结论

**合理，方向与手法都对，可以放心发布。** 这次动的是最核心的翻页逻辑，但风险控制做得很克制——IO 算法逐字未改，只是"搬家 + 加锁"；配置格式迁移还先写了平台行为探针再动手。我独立复核后确认：**行为等价**、**老配置兼容**、**打包产物正确**。

需要follow-up的只有一处引擎隐患（当前被 UI 守卫挡住、线上碰不到）和两处体验/健壮性问题，详见第四节。

## 二、这次重构做对的地方

1. **风险控制**：把最容易出问题的字节级读取逻辑原样搬走（`readLines`/`appendLine` 一字未动），只把"页码 + 指针 + 定位"的**编排**挪进引擎。等价性几乎是构造上就成立的。
2. **修掉了真实的并发缺陷**：旧实现是"EDT 上先改 `currentPage` 字段 → 再丢后台任务读页"，两步之间手动翻页与 TTS 取页可以交错，出现"各推进半步"。`BookPager` 用一把锁把"定位 + 读页 + 推进页码"整体串行，这个诊断是准的。
3. **异常处理**：旧 `readBook` 把 `e.getMessage()` 当正文返回——异常文本会混进"助手回复"里渲染，伪装直接露馅。现在统一抛给 `runIoAsync` 转成提示语。
4. **TTS 的两个真 bug**：`redirectErrorStream(true)` 又不排空管道 → `waitFor()` 可能死锁（macOS/Linux 上偶发卡死）；`isActive()` 区分"仍在运行"与"已被请求停止"，解决"停止后立刻再点没反应"。
5. **老板键**：`AtomicBoolean` 保证全局监听只注册一次（旧实现每次建窗都 `addAWTEventListener` 且永不注销），`KEY_PRESSED/RELEASED` 边沿触发解决按住不放连续切换，项目关闭时移除实例并 `stopTts`。
6. **配置迁移的工程手法**：先写 `XmlProbe` 弄清 `XmlSerializer` 的三个坑（同名 is-getter 会让字段被静默丢弃、无 `@Attribute` 的字段会写成 `<option>` 污染格式、`@Transient` 的作用点），再迁移，再写 `StateCheck` 守兼容。这是"把不确定变成可验证"的正确顺序。
7. **注释质量**：阈值、取舍、踩过的坑都写了"为什么"（例如 `linesPerPage` 为什么用 volatile 而不加锁），对后续维护非常友好。

## 三、问题清单

### P1 · `BookPager.turnBack()` 没有下限保护，越界后会污染指针缓存

复现（`.workbuddy/tools/PagerEdgeCheck.java`，当前 2 条 FAIL）：

- 首页连续"上一页"两次 → `currentPage = -10`，`displayPage()` 算出页号 **-1**（伪装里的"上下文进度"变成负数）；
- 更严重的是之后 `jumpTo(10)` 返回的是 **L21 而不是 L11**——错位 10 行。

根因：`turnBack()` 直接做 `currentPage -= linesPerPage * 2`，没有夹到 0；而 `readForwardLocked()` 在 `currentPage % 200 == 0` 时写 `seekDictionary[currentPage] = 当前位置`——当 `currentPage` 被算成负数、加回 `got` 后正好落回 0 时，写进去的却是"读完第 N 行之后"的偏移，于是缓存里的"第 0 行"是错的，后续任何从缓存 0 出发的定位都会整体错一页。

现状与定性：`MainUi` 的守卫 `currentLine() / lineCount <= 1` 拦住了用户可达路径，**线上碰不到**；而且这段代码在重构前就存在（`481ca58` 的 `readBook` 里同样是这行 `put`），**不是这次引入的回归**。但它把引擎的正确性寄托在调用方的守卫上，与"引擎自己保证页码/指针一致"的重构目标不符。

建议：`turnBack()` 里 `currentPage = Math.max(0, currentPage - linesPerPage * 2)`（另一分支同理），并给缓存写入加 `currentPage > 0` 条件。

### P2 · 读取失败的提示会把原始异常消息贴进"助手回复"

`runIoAsync` 的失败分支：`setNoticeText("无法读取当前工作区上下文：" + e.getMessage())`。`IOException` 的消息常见形态是 `D:\books\凡人修仙传.txt (系统找不到指定的文件。)` 或英文技术提示——既不好看，也把真实文件名/路径暴露在伪装界面上。

建议：界面只给固定话术（"未能定位工作区上下文，请检查文件是否还在"），把 `e` 交给 `LOG.warn`。

### P2 · 老板键的按住状态可能卡住

`bossKeyDown` 只在 `instances` 里找到 keyCode 相同的实例时才复位。若按下期间实例被移除（项目关闭），或热键在按住期间被改，抬起事件匹配不到任何实例 → `bossKeyDown` 永远为 `true` → **老板键失效直到重启 IDE**。

建议：按下时记下触发的 keyCode，抬起时与记录值比较；或在 `instances` 为空时也复位。

### P3 · 其余可选项

- 全局 AWT 监听器是 lambda，拿不到引用也就无法注销；插件动态卸载时会残留（IDE 里通常"禁用需重启"，影响有限，但值得在注释里点明）。
- 切书/关窗时旧 `BookSource` 的 epub 临时文件与图片目录仍靠 `deleteOnExit` 兜底（与旧行为一致，未变差）；若要做到"不重启也不累积"，需要给 `BookSource` 一个显式的 `close()` 并在切书时调用。
- `refresh()` 里 `bookPath` 为空时 `bookChanged` 恒为 true → 每次刷新都重建引擎（无书状态下无害，可用 `hasBook()` 短路）。
- `PagerCheck` 建议补三个用例：`\r\n` 换行（我已验证当前实现正确）、越界 `turnBack`、`jumpTo` 越界（`MainUi` 会夹到 `totalLine - 1`，引擎层不夹）。
